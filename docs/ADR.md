# Architecture Decision Record

One row per decision. A decision that is later changed is not edited: it is marked
`Superseded by ADR-xx` and a new row is added. Behaviour changes also get a row in
[REVISIONS.md](REVISIONS.md).

| ID | Date | Decision | Why | Alternative rejected | Status |
|---|---|---|---|---|---|
| ADR-01 | 2026-11-26 | Use the official MCP Python SDK **v2** (`mcp==2.3.0`): `MCPServer`, `@mcp.tool()`, `Client`. | It is the current release; docs checked on this date. The v1 `FastMCP` API is the older line. | v1.x (`FastMCP`): still published, but not where the docs point. | Accepted |
| ADR-02 | 2026-11-26 | SQLite file, stdlib `sqlite3`, no ORM. | Brief needs persistent local storage; plain SQL keeps every query readable and explainable. | SQLAlchemy: more to learn and explain for five tables. | Accepted |
| ADR-03 | 2026-11-26 | The database prevents overspending: every write runs in `BEGIN IMMEDIATE`; approval is a guarded `UPDATE ... WHERE allocation - committed - paid >= amount`; `CHECK` constraints on `funds` are the backstop. | Over stdio each client is its own server process, so an in-process lock protects nothing. | In-memory lock (wrong across processes). Read balance then write (two processes can both pass the check). | Accepted |
| ADR-04 | 2026-11-26 | Money is stored as integer cents. Input is a string of dollars with exactly two decimals (`"300.00"`). | Integers are exact. A two-decimal string cannot be confused with cents, and a bare `300` is rejected instead of guessed. | Float (inexact). Integer cents as input (a model can be off by 100x). `{dollars, cents}` pair (verbose). | Accepted (user's call) |
| ADR-05 | 2026-11-26 | `funds` stores `committed_cents` and `paid_cents`; available is derived as `allocation - committed - paid`. | Stored counters let the guarded `UPDATE` and the `CHECK` constraints work. Tests recompute the same numbers from `requests`, giving an independent cross-check. | Derive everything from `SUM(requests)`: one source of truth, but no DB-level constraint to stop an overspend. | Accepted |
| ADR-06 | 2026-11-26 | Caller identity comes only from the `ASSISTANCE_STAFF_ID` environment variable and is resolved against the `staff` table on every tool call. No tool takes a staff, role or nonprofit argument. | Brief: trusted fixture identity from launcher/env; arguments and stored text must not grant permissions. | Identity as a tool argument (the caller could claim any role). | Accepted |
| ADR-07 | 2026-11-26 | Missing or unknown identity fails each tool call with `UNAUTHENTICATED`; the server still starts and lists tools. | The model gets a readable error, and the case can be tested through MCP. Tool names are not sensitive. | Refuse to start: fails closed earlier, but the client only sees a dead process. | Accepted |
| ADR-08 | 2026-11-26 | A record in another nonprofit returns `NOT_FOUND` with the same text as a record that does not exist. Role is checked before any lookup. | A caller must not learn that another nonprofit's record exists. Checking role first means `FORBIDDEN` never depends on the record. | `FORBIDDEN` for cross-nonprofit (confirms the record exists). | Accepted |
| ADR-09 | 2026-11-26 | Approve, reject and pay are idempotent by state: a repeat returns success with `replayed: true` and moves no money. Status is checked before funds. | Retries after a timeout are normal for MCP clients; a retried approval must not get a false "insufficient funds". | Return an error on repeat (caller must work out the first call succeeded). | Accepted (user's call) |
| ADR-10 | 2026-11-26 | `create_request` requires an `idempotency_key`, unique per case worker. Same key + same details returns the original; same key + different details is `IDEMPOTENCY_CONFLICT`. | A retry must not create a second request, and two genuine identical requests must stay possible. | Optional key (a retry without it still duplicates). Content matching (blocks genuine identical requests). | Accepted (user's call) |
| ADR-11 | 2026-11-26 | Business errors are raised as the SDK's `ToolError` with the text `[CODE] what happened. How to fix it.` | SDK docs: `ToolError` reaches the model as `is_error=true` text; a failed call has no structured content, so the code has to live in the text. | `MCPError` (protocol error; the model sees nothing). Returning an error object as a normal result (`is_error` would be false). | Accepted |
| ADR-12 | 2026-11-26 | Role permissions and status transitions live in two tables in one module (`rules.py`); nothing else decides either. | Both are likely to change; one place to edit, one place to read. | Checks scattered through tool functions. | Accepted |
| ADR-13 | 2026-11-26 | The random-sequence test uses seeded `random`, not Hypothesis. | No extra dependency, every line is plain Python, failures reproduce from the printed seed. | Hypothesis stateful testing: shrinks failures, but adds a library to learn and explain. | Accepted |
| ADR-14 | 2026-11-26 | Reject takes an optional free-text reason, stored and returned as data. | Useful to the case worker; small. Not in the brief, so recorded as an assumption in the PRD. | Required reason (a rule the brief does not ask for). No reason field. | Accepted (user's call) |
